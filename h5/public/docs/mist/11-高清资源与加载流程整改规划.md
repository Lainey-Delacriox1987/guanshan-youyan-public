# 高清资源与加载流程整改规划（先规划后执行）

用户要求：恢复之前的清晰度，同时解决慢加载；不接受以768px低分辨率放大替代优化。日期：2026-10-26（用户时区）。

## 不可退让的验收线

- 默认主场景至少使用现有原画的1672×941原始像素，不再缩小到768px作为桌面主背景。
- 先比较原尺寸WebP/AVIF的压缩质量、体积与关键细节，再确定编码；保留原PNG，不生成替代画面。
- 未准备完成时显示加载界面，完成下载和解码后再开放场景；不用模糊占位冒充已加载。
- 首次加载只请求当前场景，后续按章节预载，避免Base64全图阻塞应用脚本。
- 保留既有进度、证据、对话与备忘。

## 执行顺序

1. 诊断：记录旧版本资源分辨率、原PNG/现有WebP体积；测线上HTML/静态图的传输与首字节时间，区分代码与托管线路因素。
2. 编码试验：在1672×941上生成候选高质量WebP、AVIF，核验PSNR/像素对比和200%人物/货箱细节；兼容路径保留WebP。
3. 实现：小型资源清单、默认高质量图片、真实下载进度、解码完成门控、单任务下一关预载、重复请求去重、内容哈希与缓存、失败可重试。
4. 验证：首入场/切关/缓存/弱网/失败/存档恢复，双结局回归；同时审视1920/2048桌面截图与原图细节。
5. 发布：通过检查后覆盖同一Netlify站点，核实线上默认清晰度及资源选择。更新发布记录与离线包。

## 参考与边界

Unity Addressables预下载与缓存：https://docs.unity.cn/Packages/com.unity.addressables%401.21/manual/remote-content-predownload.html
浏览器资源优先级：https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/fetchpriority

若真实公网线路吞吐仍明显不足，压缩和缓存无法消除物理传输时间。先记录证据，再说明剩余限制；不编造“所有网络秒开”，不擅自付费或变更站点访问权限。
